# Главное меню бота: три категории на кнопках, роль — вторым шагом

Дата: 2026-08-13 · Статус: утверждён

## Цель

Заказчик не принимает главное меню в виде одного интерактивного списка из семи
строк: после приветствия контакт видит свёрнутый список, который надо раскрыть
кнопкой «Выбрать». Нужны настоящие reply-кнопки, видимые в чате сразу, и
верхний уровень — по видам услуг, а не по роли контакта: сначала «аренда /
ремонт / водитель», и только внутри выбранного вида — «я предлагаю» или
«я ищу». Третьим слотом на каждом экране второго шага идёт сквозной пункт
«Мои объявления», к виду не привязанный.

## Ограничение, определяющее решение

WhatsApp Cloud API даёт **максимум 3 reply-кнопки в одном сообщении**
(`ScenarioValidator::MAX_BUTTONS`, подпись — до 20 символов). Валидатор
блокирует публикацию узла с четвёртой кнопкой; в обход валидатора запрос к Meta
упал бы целиком — количество кнопок при отправке не проверяется.

Пунктов у заказчика четыре, а в сообщение помещаются три — значит один обязан
уехать на второй шаг. Уезжает «Мои объявления»: это единственный пункт, который
не задаёт вид объявления, и на экране второго шага для него свободен третий
слот, потому что ролей внутри вида всего две.

### Почему это не противоречит прошлому решению

Предыдущая спека (`2026-08-13-main-menu-two-step-buttons-design.md`, откачена)
отвергла группировку «вид → роль» с формулировкой «верхних пунктов получалось
четыре — на кнопках не помещаются». Вывод был сделан в предположении, что «Мои
объявления» обязаны жить на первом шаге. При ролевой группировке второй шаг
занимали три вида, и свободного слота внизу не оставалось — кабинет был
вынужденно поднят наверх.

При группировке «вид → роль» второй шаг занят только двумя ролями. Это и
освобождает третий слот, снимая исходное ограничение.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Формат меню | Два шага на кнопках; узлов-списков в графе главного диалога не остаётся. Собственные интерактивные списки AI-блоков (выбор одноимённого места, выдача поиска) сохраняются — они не часть меню |
| Порядок группировки | Вид услуги → роль |
| Подписи первого шага | «Аренда спецтехники», «Ремонт спецтехники», «Водитель / машинист» — все три дословно повторяют названия видов в каталоге и админке (`ListingKind`), чтобы терминология была одна везде |
| Подписи второго шага | Формулировки заказчика: «Я сдаю спецтехнику», «Я ищу спецтехнику», «Я мастер», «Я ищу мастера», «Я водитель», «Я ищу водителя» — каждая понятна вне контекста вопроса |
| «Мои объявления» | Третья кнопка на каждом из трёх экранов второго шага, все три ведут в один блок CTA. Кабинет общий, по виду не фильтруется |
| Видимость кабинета | Кабинет перестаёт быть пунктом верхнего уровня: чтобы попасть в него, надо сначала открыть любой раздел. Это принятая цена решения, подсказки в тексте первого шага не добавляем |
| Кнопка «Назад» | Не добавляется: третий слот второго шага занят кабинетом |
| Возврат к другому разделу | Нажатием кнопки первого шага, оставшейся выше в чате. Бот сразу открывает экран второго шага выбранного раздела — сообщение первого шага повторно не отправляется, показать три раздела заново нельзя |
| Нераспознанный текст | Механика прежняя: выход «Любая другая фраза» не подключён, бот повторяет текущий шаг. Но набор распознаваемых фраз сужается — совпадение по названию и по номеру ищется только среди вариантов текущего экрана |
| Приветствие | Остаётся отдельным текстовым блоком с прежним текстом; повторное обращение по-прежнему идёт сразу к меню, минуя приветствие |
| Id вариантов | Все семь прежних id сохраняются без переименования и ведут туда же, куда вели |

## Структура меню

| Узел | Тип | Текст | Кнопки (id → подпись) |
|---|---|---|---|
| `main_menu` | кнопки | Выберите раздел. | `kind_rental` → Аренда спецтехники<br>`kind_repair` → Ремонт спецтехники<br>`kind_driver` → Водитель / машинист |
| `menu_rental` | кнопки | Аренда спецтехники. Что вам нужно? | `rent_out` → Я сдаю спецтехнику<br>`rent_seek` → Я ищу спецтехнику<br>`my` → Мои объявления |
| `menu_repair` | кнопки | Ремонт спецтехники. Что вам нужно? | `master` → Я мастер<br>`master_seek` → Я ищу мастера<br>`my_repair` → Мои объявления |
| `menu_driver` | кнопки | Водители и машинисты. Что вам нужно? | `driver` → Я водитель<br>`driver_seek` → Я ищу водителя<br>`my_driver` → Мои объявления |

Все подписи укладываются в лимит 20 символов; самая длинная — «Водитель /
машинист», 19, запас один символ. Подписи первого шага дословно равны названиям
видов, поэтому переименование вида длиннее 20 символов уронит публикацию
сценария: лимит кнопки становится ограничением и на формулировку вида.

Текст узла `menu_driver` во множественном числе — это фраза-обращение, а не
термин; терминологическое требование распространяется на подписи кнопок, а не
на текст сообщения.

Текст приветствия не меняется. Текст первого шага меняется с «Выберите, что вам
нужно.» на «Выберите раздел.»: кнопки теперь называют разделы, а не действия.

## Маршруты

- `start` → приветствие → `main_menu`; выход «Повторное обращение» →
  `main_menu` (оба без изменений).
- `main_menu`: `kind_rental` → `menu_rental`, `kind_repair` → `menu_repair`,
  `kind_driver` → `menu_driver`.
- `menu_rental`: `rent_out` → `collect_rental`, `rent_seek` → `search_rental`,
  `my` → `my_listings`.
- `menu_repair`: `master` → `collect_repair`, `master_seek` → `search_repair`,
  `my_repair` → `my_listings`.
- `menu_driver`: `driver` → `collect_driver`, `driver_seek` → `search_driver`,
  `my_driver` → `my_listings`.
- Выходы AI-узлов, тексты после сбора и после поиска, блок «Мои объявления» —
  без изменений.

Машинные значения, чтобы не домысливать: тип узла-меню на кнопках — `buttons`;
выход варианта именуется `option:{id}`; каждый узел несёт координаты холста
`x`/`y` — три новых узла размещаются между меню и AI-ветками.

Ветка меню по-прежнему задаёт вид объявления: узлы AI не меняются, вид на них
уже проставлен.

## Почему id обязаны сохраниться

Маршрутизация кнопок идёт строго по машинному id и работает на любом шаге, а не
только на том, где кнопка показана (см. `docs/modules/bot-constructor.md`).
Кнопки прежней версии сценария остаются висеть в чатах контактов. Сохранив id,
мы оставляем их рабочими: нажатие «Ищу мастера» из старого списка ведёт в ту же
ветку поиска ремонта. Переименуй мы id — контакт получил бы ответ «кнопка
устарела».

У этого правила есть приоритет, который стоит назвать явно: проверка мягкого
обновления срабатывает раньше маршрутизации по id. Контакт, стоящий в момент
публикации на прежнем `main_menu`, первым сообщением получает мягкий сброс, и
это нажатие никуда не маршрутизируется — ветку он выберет заново уже на новом
меню. Со всех остальных шагов (AI-блоки, тупиковые тексты) старые кнопки ведут
в свои ветки сразу.

Поэтому все шесть ролевых id переезжают на новые узлы как есть, а `my`
сохраняется на экране аренды. Пять новых id (`kind_rental`, `kind_repair`,
`kind_driver`, `my_repair`, `my_driver`) добавляются рядом.

Два запрета при выборе новых id:

- категорию нельзя назвать `driver` — этот id занят ролью «Я водитель»;
- ни один вариант нельзя назвать `my_listings` — такой id перехватывается
  обработчиком ответов на уведомления до входа в граф и до сценария не дойдёт.

Три кнопки «Мои объявления» получают разные id: владелец варианта ищется по
первому совпадению id в графе, поэтому одинаковые id молча схлопнули бы три
выхода в один, а валидатор такого не ловит. Разные id делают маршруты явными.
На подпись это не влияет — она у всех трёх одна.

## Нажатие кнопки меню изнутри AI-анкеты

Поведение не меняется, но масштаб растёт: в чате теперь копятся кнопки четырёх
меню — двенадцать вариантов вместо семи. Нажатие любой из них изнутри
незавершённой AI-анкеты трактуется как «хочу не это»: рабочая память
ассистента обнуляется, уже созданный черновик объявления остаётся в админке
несобранным и заново не подхватывается. Это осознанно сохраняемое поведение
движка; менять его в этой задаче не будем.

## Число нажатий

Двухшаговое меню не удлиняет путь. Интерактивный список тоже требовал двух
касаний: раскрыть кнопкой «Выбрать» и выбрать строку. Стало: выбрать раздел и
выбрать роль. До кабинета было два касания и осталось два — но теперь любые два
касания начинаются с выбора раздела, даже если контакт шёл только в кабинет.

## Активные диалоги при публикации

Контакт, ждущий на прежнем `main_menu`, попадает под правило мягкого
обновления: набор вариантов узла изменился по существу — значит мягкий сброс.
Сброс идёт от блока «Старт», поэтому контакт, уже завершавший диалог раньше,
попадает сразу в новое меню, а остальные увидят приветствие и следом меню. Это
желаемое поведение. Контакты, стоящие на AI-блоках, публикацией не
затрагиваются.

## Вне скоупа

- Изменения движка, валидатора, `DereuMessenger` и редактора сценариев: тип
  блока «кнопки», маршрутизация по id и мягкое обновление уже поддерживают всё
  нужное. Меняется только определение типового сценария.
- Поддержка секций и описаний строк в интерактивном списке — при выбранном
  варианте не нужна.
- Кнопка «Назад» и подключение выхода «Любая другая фраза».
- Возврат в меню после завершения ветки: тексты «после сбора» и «после поиска»
  остаются тупиковыми, как сейчас.
- Кнопка «В меню» в тупике поиска, которая сегодня завершает диалог вместо
  возврата в меню, хотя документация утверждает обратное. Расхождение реальное,
  но лежит вне меню и выносится в отдельную задачу.
- Судьба черновика при уходе из AI-анкеты по кнопке меню.
- Сценарии «Новая заявка» и «Продление объявления».

## Тестирование

`tests/Feature/InstallDefaultBotScenarioTest.php` — существующие проверки
семистрочного списка заменяются на:

1. Четыре узла-меню типа «кнопки», у каждого ровно свои три варианта в заданном
   порядке; узлов типа «список» в главном диалоге не осталось. Этот же пункт
   закрывает уникальность id — состав вариантов каждого узла зафиксирован
   поимённо.
2. Маршруты первого шага: каждая категория ведёт на свой экран второго шага.
3. Маршруты всех шести веток видов ведут в свои AI-узлы с прежними парами
   задача + вид; все три варианта «Мои объявления» — в блок CTA.
4. Прежние семь id вариантов сохранены и разрешаются в те же ветки (защита от
   переименования, ломающего висящие в чатах кнопки).
5. Типовой сценарий проходит валидатор: ни один узел не превышает три кнопки,
   ни одна подпись — двадцать символов. Уникальность id валидатор не проверяет,
   её держит пункт 1.

Прогон — только `make test test_args="--compact --filter=..."`.

## Выкатка

Правка меняет типовой сценарий в коде. Уже опубликованный на проде сценарий
перезаписывается только запуском `bot:install-default-scenario --force`, который
затирает ручные правки графа в админке и переписывает все три типовых сценария,
а не только главный диалог.

Если граф на проде правили руками, ручная пересборка в редакторе сценариев —
**не** равноценный запасной путь: редактор не даёт задать id варианта и
генерирует его случайно, поэтому собранные вручную кнопки получат новые id и
висящие в чатах кнопки перестанут работать — ровно тот исход, который эта спека
объявляет недопустимым. Сохранить id-контракт при ручном пути можно только
прямой правкой JSON графа или доработкой редактора. Выбор фиксируется при
внедрении, вне этой задачи.
